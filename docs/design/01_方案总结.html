三条差异，按重要性排

① 发起方向：push 而非 pull。 所有 AI 助手类产品都要求用户主动发起。但这个人群的定义性特征就是不会主动—— 手机上常用 App 只有 3–7 个，60+ 网民仅约 30% 能独立完成"出示健康码"。 对不会主动的人做 pull 型产品，等于没有产品。

② 通用知识 vs 个人档案。 阿福能告诉你"氨氯地平是什么"，但答不了"你今天早上 8 点那片白色的还没吃"。 后者需要一份经子女逐条确认过的个人用药档案——这是我们唯一的、也是可累积的资产。 通用医学知识是大厂的强项且已商品化；个人档案是靠上门、靠子女、靠时间一份份攒出来的。

③ 有没有"确认"这个动作。 没有确认闭环，就没有事实层：答不了"我今天吃了没"、无法通知子女、无法发现方案过期。 这一个按钮，是 P3 全部价值的唯一来源。

为什么大厂不会下沉到这一层

阿福 3000 万月活验证了市场存在，但它很可能不会来抢这块——大厂做的是流量产品， 需要 DAU 规模，必然优先服务能自主使用的人群（它 55% 用户来自三四线， 但那多半是"会用 AI 的中老年人"，不是 75+ 独居失能老人）。

而我们这一层的获客不走应用商店，走子女；交付要上门装机； 留存靠和社区、护工绑定。这是脏活，而脏活恰恰是不会被平台顺手做掉的护城河。 真正的壁垒不是模型能力，是那份一户一户攒出来的、经人确认过的用药档案。

老人端交互：按闹钟的心智模型设计

一次设计返工：为什么放弃"只有一个按钮"

原设计只给「吃了」，靠沉默即未服用来表达"没吃"。但它有一个致命场景： 老人在公交车上／广场舞／亲戚家，药在家里。此时唯一能让声音停下来的操作是「吃了」—— 设计本身在逼他撒谎，然后你再去分析他的数据为什么不可信。

结论：给出一个诚实的出口，比任何置信度算法都有效。 多出来的按钮不违反"操作预算 = 一次点击"，因为闹钟的稍后/关闭是已经学会的模式—— 这是它和"随便再加两个按钮"的本质区别。

三个按钮的措辞
「吃了」·「等会儿吃」·「这次不吃」
全是口语。不用"已服用／稍后提醒／跳过／取消"——那是 App 黑话。 「这次不吃」中的"这次"是刻意的：强调只是这一顿，不是停药。
视觉层级替代按钮数量
主按钮约占屏幕 40%，次级两个各约主按钮的 55% 高度、灰底。 90% 的情况下老人只会看见那个绿色大块。
全部是点击
绝不用滑动。老人手指干燥、手抖，滑动失败率极高。安卓闹钟的左右滑是反面教材。
不隐藏次级按钮
不做"点开更多"的渐进披露。藏起来的 UI 对这个人群等于不存在—— 可发现性 > 界面干净。

「这次不吃」的四个原因——全产品信息密度最高的一次点击

选项紧急度触发什么
我不在家低 仅记录。这是最重要的一个选项——它把原本会变成假"吃了"的那部分行为，转成了干净数据
药吃完了中 立即通知子女「该买药了」。老人药吃完了不主动说，是极常见且完全可预防的断药原因
今天不舒服最高 归为 SYMPTOM：立即推送子女 + 原话原声，15 分钟无响应转第二联系人
医生说停了高 子女核实 + 标记用药方案可能已过期 → 请求重拍药盒。 直接接上"方案静默过期"那条失败模式

从闹钟借什么、不借什么

✓ 借过来

  • 全屏亮屏、绕过锁屏，不是一条会自己消失的横幅
  • 声音渐强，不要一上来就最大音量
  • 不操作就不停（上限 2 分钟）——通知会自己消失，闹钟不会
  • 稍后／关闭的双出口，这是核心借鉴

✕ 不借

  • 滑动手势——对手抖／干燥手指失败率极高
  • 可自定义的稍后时长——时间选择器是灾难
  • 响完即结束——见下方"待办态"
  • 贪睡无限循环——3 次后必须转人工
和闹钟最重要的一处不同：待办态

闹钟的职责在被关掉时就结束了；用药提醒不是。响铃结束后， 屏幕上／通知栏必须常驻一张卡片：「你还没吃 8 点的药」，直到被处理或被下一次覆盖。

所以这个交互是 闹钟 + 待办 的混合体，不是纯闹钟。

仍然存在的局限（改善了，但没消失）

它记录的仍是「按了按钮」，不是「吃了药」。数据库里叫 confirmation_event， 不叫 medication_taken——命名决定下游所有解读的诚实度。

新出口带来一个新风险：老人可能一律按「等会儿吃」来逃避。 所以要监控 snooze 率——如果某人 90% 的剂次都在推迟，这本身就是高价值信号 （可能是操作困难，也可能是抗拒服药），而不是噪音。

第 11 天上门重点观察两件事：他是先拿药还是先按按钮；他会不会用那两个次级按钮。

03为什么这个架构能解决痛点

痛点机制为什么别人做不到 / 没做
P1 本地闹钟 + 语音播报 + 一个大按钮；30 分钟未确认自动升级子女 不是差异化来源，但是习惯锚点——所有其他价值都挂在这个每天被按 2–4 次的按钮上。
P2 VLM 读盒子 → 归一化 → 重复用药/PIM 检查 → 大白话语音问答 药盒硬件不知道盒子里是什么，无法回答"这两个能一起吃吗"。 84% 看不清 / 58% 看不懂，是一个阅读与理解问题，只有 VLM+LLM 能解。
P3 按钮点击流本身就是客观记录；化验单归档构成医学事实层；升级通道保留原话原声 这份记录不经过任何有立场的人。而且边际成本为零——为 P1 建的东西，直接就是 P3 的答案。
静默
过期		 化验单捕捉 = 复查事件 → 触发"药方可能变了，请重拍药盒" 这是化验单功能在 POC 里的最小职责：不是归档，是触发。归档几乎白拿。
关键的产品杠杆

P1 建立习惯 → P2 建立不可替代性 → P3 建立付费意愿。 三层共用同一套采集与同一个按钮，后两层的边际成本接近零。 而付费方（子女）和使用方（老人）在 P3 层终于对齐了。

失智场景：一个功能解决四件事

失智老人一天问 30 遍"今天星期几"。家人会说"你都问十遍了"——这对老人是伤害。 AI 可以第 30 遍还用一样温和的语气回答，这是极少数 AI 真正比人做得更好、而不只是更便宜的场景。 真正的价值在第二层：这个交互本身就是一份被动采集的认知量表——提问频率与重复间隔的变化构成纵向曲线，不需要任何人做测试。

同时解决：陪伴 早期识别 建立基线 子女决策有据 ——传统 MMSE 要去医院预约，家庭几乎不做，于是早期识别被延误 1–2 年。

但医学边界必须守住

只能说「本月日均重复提问 11 次，三个月前是 3 次」； 绝不能说「这提示认知衰退」。前者是计数，后者是行医。

04关键技术设计点

① 交付形态：安卓 APK 侧载，不是小程序

个人主体拿不到长期订阅消息（只对政务/医疗/交通/金融/教育二级类目开放）， 且医疗类目对个人完全禁止；2014 年后注册的个人订阅号无法微信认证。 「定时提醒吃药」在微信生态里对个人开发者是接口层面做不到的。 老人手机安卓:iOS ≈ 9:1，侧载可行，本地 AlarmManager + 系统 TTS 无需任何资质。

② 人在环内：AI 解析 → 子女逐条确认 → 才生效

中文药盒商品名/通用名/规格排版混乱，VLM 读错一次就是安全事故。 这条是红线，不是可优化项。永远不做全自动。

③ 检索用确定性 SQL，不用向量库

  • 召回不全是静默失败——top-k 漏掉 2 项异常，没有任何信号告诉你漏了。医疗数据不可接受。
  • 向量空间里没有"上次"——时间序在余弦相似度里不存在，而 ORDER BY date DESC LIMIT 2 是零歧义的。
  • 数据本来就是结构化的，几十份报告几千行，SQLite 全表扫描是微秒级。
  • 可追溯到原始凭证——向量只能说"这是最相似的片段"。

④ 自然语言 → 固定意图 + 槽位，不做 text-to-SQL

LLM 输出受约束的 JSON（intent 为枚举、指标名走白名单），不输出 SQL 字符串。 生成的 SQL 会绕过归一化层（写 WHERE raw_name='血糖'，漏掉记作 GLU 的行）， 而且错了没有 oracle。6 个意图 × 20 条问句 = 120 个可穷举的 CI 用例。

映射不上就拒答，绝不猜相近指标。拒绝 > 猜错

⑤ ASR 领域偏置 + 低置信度重问

把这位老人自己的药名清单作为上下文喂进识别——「苯磺酸氨氯地平」通用模型转不出来， 给了候选词表命中率大幅提升。零成本、收益最大的一个改动。 低置信度重问，不猜、不升级：重问对老人成本几乎为零，猜错代价极高。

⑥ 原始凭证永久保留

  • AI 的错误是静默的——结构化结果永远看起来工整自信。原件是唯一仲裁者。
  • 模型会升级，采集机会不会重来——存了原图/原音频才能三年后重跑历史数据。
  • 结构化必然丢弃信息——语气里的犹豫、化验单角落的手写批注。今天不知道明年什么重要。
  • 没有原始输入就没有回归测试集。

⑦ 说出口的承诺必须是真的

对一个 78 岁的人说"我问一下你女儿"而消息没发出去，等于对一个正在等待的脆弱用户撒谎。 话术必须跟着投递状态走：
入队 →「我这就去问」（将来时） · 投递确认 →「已经发给你女儿了」 · 重试耗尽 →「我没联系上，你自己打个电话」+ 满屏拨号按钮

需要持久化 outbox + 状态机（活过重启/关机），不是 fire-and-forget。 最终兜底通道是电话，它永远能用。

⑧ 升级要分诊，不做单个 escalate()

六类触发，紧急度差两个数量级：SYMPTOM（立即+原声）·MED_CHANGE（立即）· MISSED_DOSE（当日合并）·UNRESOLVED_ENTITY（每日摘要）· REGIMEN_STALE（每周）·ASR_FAILURE（不升级）。 升级通道的价值 = 它的信噪比。子女一天收 20 条噪音，两天后就静音，真正紧急的那条也进不去。

症状类原话原声直送，不许 LLM 改写——不能把"我胸口有点闷"改成"患者主诉胸闷"。

⑨ 安全边界：只做转录 / 对比 / 放大

  • 转录「血肌酐 118，参考 57–97，↑」——本来就印在单子上
  • 对比「上次 96，这次 118」——这是减法
  • 放大字号与语音
  • 「这说明你的肾功能在下降」
  • 「这个指标偏高要注意饮食」
  • 任何剂量调整 / 停药建议

越过这条就是行医，个人主体没有任何资质。 影像报告更严：只原文抽取「诊断意见」段落，一字不改、不概括—— "考虑"/"不除外"/"建议随访"每个词都有精确含义，概括必然失真。

⑩ 隐私：记录事件，不记录内容

Log that something happened, not what was said in the room.
✓ 「08:03 确认服药」「昨夜 2:17 手机被拿起」「本周重复提问 47 次」 ✕ 常开麦克风 / 摄像头 / 全屋录音

双向知情 + 分层可屏蔽：安全类事件（漏药、跌倒、症状）不可屏蔽且老人知情； 生活类老人有权说"这条别告诉我女儿"。 听起来违反直觉——但一个完全没有隐私的老人会拒绝使用这个产品。

让方案能落地的那个 framing

纯"监督护工"的产品会被消极抵抗——拔电源、说没网、替老人按按钮。 但护工同样是失真的受害者：中期失智的典型症状就是妄想指控（"保姆偷了我的戒指"）， 而护工目前毫无自证手段。
同一份客观记录，对子女是监督，对护工是免责。 明确定位成后者，护工会主动配合。这不是话术，是真实的利益一致。

如果 5 个人里真有一台 iPhone，按优先级：

  • ① 换一个安卓用户——最省事，POC 阶段样本可以选。
  • ② 只给大字用药表 + 子女端网页——把大字表设成他 iPhone 的锁屏（手动设即可）， 他仍然获得 P2／P3 的价值，只是没有每日闭环。

但 iOS 长期不能忽略，而且答案可能不是 iPhone

用 iPhone 的老人群体偏城市、偏富裕，付费意愿更高，中期必须覆盖。 但对这个人群，更好的输出设备很可能根本不是手机—— 小爱／小度智能音箱常年通电、音量大、无需导航任何界面，且已在很多中国老人家里。

这同时也是风险清单里那条的答案：如果第 11 天发现老人根本不看手机（手机在客厅充电、人在卧室）， 正确的下一步就是音箱，而不是补 iOS。

07POC 之后：迭代与产品化路径

7.1　迭代：绝大多数改动不需要新 APK

核心原则：把变化快的东西从 APK 里挪出去。 按"多久改一次"划分，就能看出真正需要重新安装的其实很少。

改动频率内容放在哪
每周 播报话术 · 按钮文案 · 追问选项 · 贪睡时长 · 重试策略 · 升级阈值 · 拒答规则 · 意图分类 全部服务端
remote config + 服务端生成播报文本
每月 药名映射表 · PIM 清单 · 检验指标映射 · 安全规则 服务端数据文件

四条机制

① Remote config——启动时 + 每天拉一次 JSON，控制话术模板、时间参数、文案、功能开关、 灰度分组。这一条解决约 80% 的迭代需求，零重装。

② 播报文本在服务端生成——APK 只负责"播"，不负责"写"。改话术 = 改服务端模板， 不动客户端一行代码。

③ 应用内自更新——国内安卓标准做法（不走 Google Play）：APK 检查版本 → 静默下载 → 拉起系统安装器。首次侧载时用户已授权"安装未知应用"，后续更新只需两次点击。

④ 断网可用——APK 必须在服务端完全不可达时照常提醒（本地缓存排程 + 系统 TTS）。 这既是可靠性底线，也是你敢于频繁改服务端的前提。

更新流程里最容易做错的一件事

那两次点击，老人做不了。所以更新绝不能设计成"弹窗让老人自己确认"：

  • 由子女在 Web 端远程触发，老人端只在非用药时段（如下午 3 点）弹一个大按钮
  • 静默下载，只有最后一步需要交互
  • 更新失败绝不能影响当天的吃药提醒——旧版本必须继续正常运行。这是铁律

另：50 个用户以内，人工远程指导完全可以接受，不要过早自动化。 灰度先发 5 个人；A/B 测试只对话术和时间做，绝不对安全逻辑做——样本量太小，且这是医疗场景。

最重要的一条：那条安全红线不只是伦理，是商业生死线

医疗器械软件的界定核心是——是否基于医疗器械数据、是否用于医疗用途（诊断／预防／监护／治疗）。 健康管理类软件若不符合这些条件，不作为医疗器械管理。

✅ 守住 转录 / 对比 / 放大、不给任何诊疗建议 → 属健康管理软件，不作为医疗器械管理，可正常上架。
❌ 一旦加上「这个指标提示肾功能下降」「建议减量」 → 落入医疗器械范畴，注册周期以年计、成本百万级，整个产品形态要重做。

换句话说：前面所有关于"只做转录对比放大"的设计约束， 不是在做道德选择题，是在决定这家公司能不能上线。越线的代价不是被批评，是重来。

一个真实的法律灰区：老人怎么"同意"

《个人信息保护法》对不满 14 周岁未成年人有明确的监护人同意规则， 但对认知受损的老年人没有对应的明确规定。

弹一份隐私协议让一位 78 岁、可能已有认知衰退的老人点"我同意"， 在法律效力和伦理上都站不住。务实方向：

  • 双签——老人 + 子女共同确认，子女侧承担告知责任
  • 告知必须有大字版和语音版，不是一堵小字
  • 老人可随时查看"系统把什么发给了谁"——这同时呼应 §04-⑩ 的隐私设计
  • 若涉及失智人群，需就监护关系单独设计流程，并咨询专业法律意见

7.3　可能更快的一条路：社区卫生服务中心

C 端上架要自己趟完上面六道门槛。而 B 端可以借用对方已有的资质主体，同时绕开应用商店（机构内分发）—— 这不只是省事，可能直接节省一年。

他们手里管着 1.15 亿 高血压患者，被考核的正是控制率，
而全国控制率只有 16.8%—— 因为他们没有任何手段知道这些人回家之后有没有吃药。

为什么社区卫生服务中心是最优先的 B 端入口

条件具体
有考核压力 国家在推家庭医生签约服务，慢病管理与控制率是核心考核指标。 《健康中国行动·心脑血管疾病防治行动实施方案(2023—2030)》明确要求控制率持续提高—— 这是自上而下的、带指标的刚需，不是"锦上添花"
有真实存量 2024 年基层医疗卫生机构服务 65 岁及以上老年人 1.41 亿， 在管高血压患者 1.15 亿。不需要拉新，人已经在册
有资质主体 医疗机构执业许可证已在手。App 备案、医疗类目、隐私合规都可由机构侧承接， 直接跳过 §7.2 的第 1、2、6 道门槛
有分发通道 签约时家庭医生当面装机——正好解决"老人不会自己下载"这个根本障碍， 而这恰恰是 C 端最难的一步
有信任背书 基层医生说的话，老人听。陌生 App 说的话，老人不听。 这对一个涉及吃药的产品是决定性的
需求方向一致 他们要的正是我们的 P3 事实层：签约居民回家后到底有没有按方案吃药。 这是他们目前完全的盲区

产品要为此调整什么

  • 加一个机构端视图：家庭医生看到自己签约的 N 位居民的确认率与异常清单， 而不是一个个查。工作量增量小（同一套数据换个聚合维度）
  • 「医生版」那页 A4 变成核心功能（原本排在 §11 的延后项）—— 近三次指标对比 + 当前用药，正是随访时最需要的东西
  • 安全边界反而更好守：机构场景里，所有医学判断本来就该由签约医生做， 产品只做转录 / 对比 / 放大，定位天然清晰
  • 数据合规由机构主导：知情同意可并入签约流程，比让老人在手机上点"我同意" 在法律与伦理上都稳固得多（呼应 §7.2 的灰区问题）

其他 B 端渠道

渠道为什么它想要备注
养老机构 / 社区养老驿站降低护理事故、留痕免责 正好对应"记录同时保护护工"的定位（§04）
保险公司（健康险）依从性↑ → 并发症↓ → 赔付↓付费能力最强，决策链最长
药企患者支持项目慢病依从性直接影响销量合规敏感，边界需谨慎设计
B 端的代价，要提前认

定制化需求多、销售周期长（公立机构决策慢）、容易被单一大客户绑架方向、 单价可能被压得很低。而且机构的 KPI 和老人的利益不总是一致—— 一旦确认率变成考核数字，就会有人替老人按按钮（§04 已警告过：这份数据绝不能当 KPI）。

务实的走法：先做一个中心的试点，不签独家、不做深度定制， 用它验证 B 端付费意愿和真实使用率，同时 C 端资质并行推进。两条路都留着。

7.4　建议的推进顺序

阶段用户量分发同时在做
POC（2 周）3–5侧载 APK验证；不碰任何资质
扩样（1–3 月）30–50仍然侧载 并行启动：注册个体工商户 → ICP／App 备案 → 软著（这几项周期长，越早越好）
机构试点（3–6 月）100–300机构内分发找 1 个社区卫生中心；验证 B 端付费意愿
正式上线—应用商店 ／ B 端依据试点结果决定主战场
一句话

资质流程是并行任务，不是前置任务。它们周期长但不消耗创造力—— 在扩样阶段就并行启动，别等到想上架时才开始，也别在 POC 阶段被它们拖住。
